Joomla 6.2.1 Known Issues and Compatibility Notes
=================================================

## Third-party Web Services extensions must use `core.api`

Joomla 6.2.1 introduces a separate `core.api` permission for accessing non-public Web Services endpoints. By default, `ApiDispatcher` checks this permission before dispatching a request. Previously, many API controllers checked `core.manage` instead.

This is an intentional access-control change, but third-party Web Services extensions may require updates. Extensions that continue to rely on `core.manage` for API access or that use a custom dispatcher not extending `ApiDispatcher` may encounter unexpected authorization results.

### Required changes

1. Add `<action name="core.api" title="JACTION_API" />` to the component's `access.xml` and replace checks for `core.manage` **where they control Web Services access** with `core.api`. Keep `core.manage` for ordinary component-management permissions.
2. If the API component provides a custom dispatcher, extend `Joomla\CMS\Dispatcher\ApiDispatcher` rather than `ComponentDispatcher`. If overriding `checkAccess()` or `dispatch()`, preserve the API access check.
3. Test with a user who has `core.login.api` but not `core.api`, and with a user who has the component's `core.api` permission. Additional action permissions such as `core.create`, `core.edit`, and `core.delete` are still enforced.

During the update, existing explicitly stored `core.manage` ACL rules are copied to `core.api` where available. Review the resulting permissions if API access should differ from administrator access.

### Note for site administrators: previously public API routes may require authentication

Joomla 6.2.1 only considers a Web Services route public when its `public` option is explicitly set to the Boolean `true`. Previously, other values such as `1` were also treated as public. As a result, some third-party API endpoints that worked without authentication may now require an API login or return an authorization error.

This is a security-conscious change. If an integration is affected, check for an updated version of the extension or contact its developer. Only routes intentionally designed for unauthenticated access should be marked public.

See [Removed and Backward Incompatibility](../removed-backward-incompatibility.md#web-services-use-coreapi-in-joomla-621) for code examples and migration details.
